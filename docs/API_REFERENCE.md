| **Interface Auth** | | |
| `/auth/local` | POST | Interface-local owner login. Accepts form fields `username` and `password`, verifies against deployment env, and writes a signed `mycelis_web_session` cookie. |
| `/auth/google/start` | GET | Starts Google Workspace OIDC login when `MYCELIS_AUTH_GOOGLE_*` env is configured. |
| `/auth/google/callback` | GET | Completes Google OIDC login after validating and consuming the short-lived OAuth state. The callback verifies token audience, verified email, and the configured Workspace-domain policy, maps only `MYCELIS_AUTH_ADMIN_EMAILS` to admin, then writes a signed web session. Every exit clears the state cookie and returns a normalized login error; provider response bodies, tokens, exception messages, and client secrets are not logged or returned. |
| `/auth/session` | GET | Returns current Interface session posture: authenticated user, role, provider, and enabled login providers. |
| `/auth/logout` | POST | Clears the Interface web session and redirects to `/login`. |

Interface proxy routes sign the current web session into `X-Mycelis-Web-Identity` and `X-Mycelis-Web-Identity-Signature` when calling Core with the deployment API key. Core verifies the HMAC with `MYCELIS_WEB_IDENTITY_FORWARD_SECRET` or `MYCELIS_WEB_SESSION_SECRET` before using that principal for governance/audit context and `actor_identity` metadata. Invalid forwarded identity headers fail closed; missing headers retain the local API-key identity. When no browser session exists, document navigations to protected API or workspace-file URLs redirect to `/login?next=...`; programmatic fetches still receive structured `401` JSON with `{"ok":false,"error":"authentication_required"}` so components can handle the state without losing request context.

| **Chat & Cognitive** | | |
| `/api/v1/chat` | POST | Soma/Admin chat. Runtime-state, Workspace V8 design-state, search-capability, and plain service-inventory questions answer directly; service-inventory answers use user-facing capability language and reserve raw tool/MCP identifiers for explicit technical inventory asks such as `show internal tool names` or `debug MCP status`. Freshness-oriented search prompts call configured Mycelis `web_search` before the NATS Admin-agent path only when the latest request is not a governed mutation/team-creation/delegation prompt. Requests may include a focused `team_id`; blank/root Soma context resolves to `admin-core`, while focused-team Soma turns, proposal bus wiring, and team expressions preserve the selected team so team-scoped work does not leak back to root context. Requests may also include optional `continuation_context` for delivered-output re-entry, currently shaped as `{ kind: "output", title, reference, proof }`; this attaches grounding context and audit metadata only, while mutations, team handoffs, and execution still follow the normal approval path. While correlated work is active, the Interface may add `active_work_context={type:"team_work",id,run_id,team_id,work_item_id,project_id?,steering_id}`. Core validates its identifiers and current run ownership; explicit change guidance is committed as status, mission event, work update, interaction, and idempotent dispatch-outbox work in one PostgreSQL transaction, then published asynchronously to the team's canonical NATS command subject. Team command ingress recognizes steering metadata, deduplicates it durably, and publishes the guidance to active member interjection channels without entering the normal job/result-correlation queue. Soma returns a concise acknowledgement and stays conversational. Ordinary questions remain ordinary chat and do not steer the team. Chat responses may include `continuation_intent` (`follow_up`, `inspect`, `update`, `fork`, or `route`) so the UI can explain how Soma understood the output reply without treating context as approval. Proposal payloads include `bus_scope`, `nats_subjects`, `execution_mode`, and `work_intent`; explicit `create_team` proposals use only the requested team's command/status/result subjects, not a fallback admin-core bus. `work_intent.output_contract` names the expected deliverable shape (`document`, `table`, `code_script`, `media`, `dataset`, `app_package`, or mixed output), primary deliverable, retention class, launch hint, and validation expectations so teams know what must be returned without exposing runtime topology by default. Explicit team requests can retain concrete output asks such as `write_file`, `generate_image`, and `save_cached_image` in the same proposal. Before persisting a proposal that includes `generate_image`, Core checks the configured image provider; unavailable or API-disabled providers return a structured `media_provider_not_ready` setup blocker without creating a proposal, team, run, or planning deliverable. Inferred generic `create_team` calls start lead-only with `initial_member_count=1`, a bounded `recommended_member_limit`, and explicit expansion guidance; explicit specialist-output asks may carry a bounded `agents` roster, media capability requirements, and first retained deliverable steps in the same ExecutionContract. Chat responses may include `execution_summary` so the UI can show intent, Soma understanding, execution shape, capability use, outputs, proof, audit/recovery state, and next step. |

Use this for temporary-team cleanup so delivery tests stay bounded to 1-3 targeted teams instead of accumulating stale runtime teams. |
| `/api/v1/teams/detail` | GET | Team detail with agent rosters, delivery targets, and status |
| `/api/v1/teams/{id}/work` | GET/POST | Durable team-work items for Soma/Council/operator management. GET accepts `limit` and `include_archived=false` for queues that should hide cleared work while preserving retained history. `view=attention` further limits the response to unarchived `needs_operator`, `reviewing`, `output_ready`, or `degraded` rows plus any row explicitly marked `needs_operator=true`; unsupported view values return `400`. Responses include normalized `outcome_health` (`healthy|waiting|running|degraded|blocked|completed|archived`) in addition to the source-specific lifecycle `state`; primary UI uses outcome health while Inspect may expose lifecycle state. `create_team` items may only be `new` or `briefed`; delegated or deliverable work may be `queued`, `running`, `needs_operator`, `reviewing`, `output_ready`, `degraded`, `paused`, or `archived`. Confirmed `create_team` actions now persist a non-active team-shell item, while confirmed delegated work queues a real item and confirmed retained deliverables persist output-ready items with `run_id`, `intent_proof_id`, `contract_id`, `proof_id`, `audit_refs`, retained `output_refs`, and a quiet `target_ref` where stable user-facing destinations exist. |
| `/api/v1/teams/{id}/work/ask` | POST | Submit one bounded runtime-team ask and persist the result as Active Work truth. Body accepts `message` or structured `ask`, optional `async`, `summary`, `actor_ref`, `timeout_seconds` capped at `60`, `expected_outputs`, `expected_proof`, `capability_requirements`, `governance_posture`, and bounded `payload`. The endpoint creates a durable delegated `TeamWorkItem`, records queued status, updates the work item, and writes the ask interaction in one transaction before returning durable work state. Queued/running async work receives a queryable PostgreSQL recovery deadline. With `async=true` it records durable dispatch tracking before publishing, then publishes and flushes a governed command envelope to `swarm.team.{id}.internal.command` containing `work_item_id`, team metadata, expected outputs/proof, and request context, then returns `202` with `accepted=true` and `dispatch_state=published`; this API acknowledgement means the command was committed and handed to transport, not yet accepted by a consumer. A team consumer must atomically claim the PostgreSQL command receipt before work begins and then publishes a correlated `Team accepted work` status. Replayed commands are rejected across process reconstruction. Team runtime correlation is FIFO for plain responses and preserves explicit response `work_item_id` values. Correlated status/result signals advance the original work and terminal states clear its deadline. If no terminal signal arrives, the database-backed reconciler survives Core/NATS restart, projects `team_work_recovery_deadline_exceeded` with Soma recovery guidance, and derives a terminal `degraded` run only after all sibling work has settled. Result projection claims a stable PostgreSQL receipt in the same transaction as status/work updates. Deliverable work with expected outputs cannot become trusted `output_ready` without retained `outputs[]` or `output_refs[]`; package-shaped work additionally requires an isolated `groups/<team-id>/generated/...` package, a present entrypoint/dependencies, and any approved interactive validation. Invalid results degrade with a specific recovery state. Valid final results record proof, update the ExecutionContract/run, and broadcast a direct Soma completion event. Durable `storage_ref` values are workspace paths rather than viewer URLs. NATS offline, publish failure, or flush failure immediately records `degraded` with recovery options and returns `202`. Without `async`, the compatibility path waits for a bounded reply and records either `output_ready` with a retained text reply/proof ref or a normalized degraded timeout/unreadable state. |
| `/api/v1/teams/{id}/work/{workItemId}/interactions` | GET/POST | Durable `TeamInteraction` records for a work item, including `source_kind`, `source_channel`, `actor_ref`, verb, summary, `payload_kind`, optional bounded payload/ref, approval ref, audit refs, and optional run/proof links. |
| `/api/v1/teams/{id}/work/{workItemId}/actions` | POST | Apply an audited operator control to a durable work item. Body uses `action=start_work|pause|resume|archive|steer|recover|verify_external_outcome` with optional `summary`, `actor_ref`, `source_kind`, `source_channel`, `payload_kind`, `payload`, `audit_refs`, and `idempotency_key`; `steer` and `recover` require either `summary` or `payload` so the audit trail records real guidance. Transition validation, status/mission event, work update, interaction, and any correlated steering outbox record commit in one PostgreSQL transaction. A run/proof-linked `steer` then dispatches asynchronously to `swarm.team.{team_id}.internal.command`; older non-correlated records remain auditable without claiming a live handoff. The endpoint returns the updated `TeamWorkItem`. Current transitions: `new|briefed|queued -> running` for `start_work`, `queued|running|needs_operator|reviewing|degraded -> paused`, `paused -> queued` for `resume`, non-archived delegated/deliverable work -> `archived`, no state change for `steer`, and `degraded|needs_operator -> queued` for `recover`. An external mutation whose side-effect state is `unknown` fails closed: generic start, pause, resume, and recovery are rejected. `verify_external_outcome` requires a non-empty observation plus `payload.result=committed|not_committed|still_unknown`; `payload.evidence_refs` is optional. Core supplies the authenticated actor and timestamp, persists the verification in WorkIntent, and records status plus interaction in the same transaction. `committed` closes the work as operator-attested without replay; `not_committed` requires a new governed Soma proposal; `still_unknown` remains degraded. Verification never dispatches or retries work. `steer` and `archive` remain separately available. Browser UI labels `archive` as `Clear from review`; this is audited retention cleanup, not deletion. For `create_team` shell records, clients should route the operator through a Soma/team ask that creates a delegated or deliverable work item before showing lifecycle controls as executable. |
| `/api/v1/teams/{id}/work/{workItemId}/status-events` | GET | Durable `TeamStatusEvent` timeline for a work item. Returns source lifecycle state plus normalized `outcome_health`; `limit` is bounded and capped at `100`. Run-linked status events also mirror into the persistent Event Spine as `mission_events.event_type=team_work.status` with normalized source, state, proof, blocked-by, next-action, and `target_ref` metadata so team work can be reconstructed from the run timeline. |
| `/api/v1/outcome-projects` | GET/POST | Durable user-facing outcome workspaces. GET returns `APIResponse<OutcomeProject[]>` with normalized `outcome_health`, retained output refs, proof refs, recovery refs, team-registry refs, run/proof links, workspace folder, source status, retention policy, and a quiet `target_ref` for revisit surfaces. `run_id` and `intent_proof_id` are preserved as text links because user-facing outcome ownership may retain runtime identifiers that are not always UUID-backed rows. POST creates an explicit project record without starting execution. Confirmed Soma proposal execution now creates an `OutcomeProject` automatically when durable team-work/output refs are produced and includes it as `data.outcome_project` in `/api/v1/intent/confirm-action`. |
| `/api/v1/outcome-projects/{id}` | GET | Read one durable `OutcomeProject` by UUID. Use this as the API-backed Revisit object for Vault and output ownership surfaces instead of reconstructing ownership only from chat or file listings. |
| `/api/v1/outcome-projects/{id}/team-registry` | GET/POST | List or attach `TeamRegistryEntry` records for an outcome project. Entries bind the project to the smallest useful lead/specialist team or agent, with role, runtime team ID, assignment reason, temporary flag, expiry, and status. Runtime team IDs remain text values so generated teams such as `trusted-outcome-live-*` do not need legacy UUID team rows. |

An identical durable same-id retry is idempotent at storage level, while a conflicting same-id manifest fails closed. |

| **Telemetry & Trust** | | |
| `/api/v1/stream` | GET (SSE) | Normalized operator-event stream. User-facing work handoffs may emit typed `thread_event` payloads with source metadata, run/work/proof targets, status, and operator-safe copy so the Interface can add compact Soma-thread cards without exposing raw NATS envelopes. PostgreSQL-backed events carry monotonic SSE `id` values. Native EventSource reconnect sends `Last-Event-ID`; Core replays newer events in order up to the bounded replay limit and emits a normalized `replay_gap` event when the cursor is invalid, persistence is unavailable, or older events were omitted. The Interface suppresses duplicate event ids. A client whose live buffer fills is disconnected so EventSource can reconnect and restore the missed range instead of silently dropping it. Idle heartbeat comments keep long team runs connected through proxy timeouts. Replay guarantees event visibility, not exactly-once team execution. |

| `/api/v1/search/sources` | GET/POST | List or add governed search sources Soma may use when policy allows. Sources can represent built-in/local search, public web providers, operator-owned local APIs, authenticated client-owned sources such as docs portals, repositories, issue trackers, file stores, or intranet search, and native `code_context` repository/code-folder sources. POST accepts a plain name, `provider`/`source_type`, `endpoint` or `base_url`, source boundary, scope (`all`, `group`, or `host` plus `scope_ref` when scoped), auth scheme, `secret_ref`, mode, sensitivity/trust defaults, status, and recovery text. `code_context` list responses may also include a `code_context` object with `scope`, `snapshot_status`, `last_snapshot_at`, `index_status`, `last_indexed_at`, optional Refresh/Repair action text, and raw `snapshot_ref`/`snapshot_digest`/`index_ref`/`index_digest` values for Inspect-only display. External/API-style sources require an absolute `http(s)` endpoint with no embedded credentials. Authenticated sources require a managed secret reference such as `SEARCH_API_TOKEN`, `env:SEARCH_API_TOKEN`, `vault:...`, or `secret:...`; raw tokens and unknown credential fields are rejected. Source creation requires the PostgreSQL-backed search source registry and fails closed when durable persistence is unavailable. |
| `/api/v1/search/sources/{id}` | PATCH/DELETE | Update or remove an operator-managed search source. | `/api/v1/input-sources` | GET/POST | List or register governed event-producing sources that feed Soma, teams, or Outcomes after validation and buffering. Sources can represent MCP callbacks, webhooks, local APIs, service buses, database/event connectors, file watchers, host probes, sensors, devices, or schedulers. POST accepts `id`, `name`, `source_type`, `adapter_kind`, scope (`all`, `group`, or `host` plus `scope_ref` when scoped), optional target Outcome/group/host ids, auth scheme, secret reference, concrete `allowed_ingress_subject`, schema ref, `buffer_mode`, buffer policy, sensitivity/trust, status, and recovery. Raw credentials are rejected; authenticated sources require managed secret refs. If omitted, ingress subject defaults to `swarm.global.input.{id}`. Wildcards are rejected, and a second source claiming an already registered ingress subject receives `409 Conflict`. The source subject belongs to the `NATS_URL` host used by this Core process. |
| `/api/v1/input-sources/{id}` | GET/PATCH/DELETE | Read, update, or remove one registered input source. PATCH uses the same validation as create. DELETE removes the source and cascades its source-owned event/latest/window buffers. |
| `/api/v1/input-sources/{id}/buffer` | GET | Read the durable buffer view for a registered source. Query params: `mode=append_log|latest_state|append_with_latest|windowed_rollup`, optional `channel_key`, and bounded `limit`. The response returns the source plus events, latest values, or window summaries so Soma and teams can reference buffered data instead of reading raw high-rate traffic directly. When PostgreSQL and NATS are healthy, Core also subscribes to the registered input ingress lane and persists matching `swarm.global.input.{source}` messages into this buffer. Unknown subjects are ignored; raw messages are normalized with source/channel/payload metadata before storage. |
| `/api/v1/search` | POST | Governed Mycelis Search API. Native and Helm defaults use `builtin_web` for token-free public web search; Compose can override to self-hosted `searxng`, and operators can choose `local_api` for an owned HTTP search endpoint or `local_sources` for retained Mycelis context. When `source_scope` is omitted, the Search API, direct Soma search, and the internal `web_search` tool infer scope from the query: ordinary or freshness phrasing such as `can you search on this topic`, `latest`, `recent`, or `popular` requests `web`, explicit local/shared/mounted-data asks request `local_sources`, and mixed requests request `all`. If `web` is requested or inferred while the active provider is only `local_sources`, the API returns a structured `web_provider_not_configured` blocker instead of presenting local no-results as public research. When `all` is requested and a public provider is configured, the API searches approved local/mounted sources and the configured public-web path, merges bounded results, and reports `source_coverage`, `local_source_count`, and `web_source_count`. If one boundary is unavailable, responses keep the available results and include `partial_source_scope`, `missing_source_scope`, and `scope_warning` instead of implying complete local-plus-web coverage. If `all` is requested against a local-only provider, responses may return available local results with `partial_source_scope=local_sources_only` and `missing_source_scope=web`. Requests may include `source_id` to route through a configured source when scope/status/auth guardrails allow it. Selected local-source, built-in web, local-API, and SearXNG-compatible sources route directly; local-API sources may use `api_token` or `bearer_token` secret refs resolved from environment variables and applied as an Authorization bearer header. Out-of-scope, missing, unavailable, unsupported, unresolvable-secret, or unsupported-auth sources return structured blockers. Responses include selected-source provenance in `data.metadata.selected_source_id`, `selected_source_name`, `selected_source_boundary`, and `selected_source_type`. Configured online search runs without a separate confirmation prompt when `MYCELIS_SEARCH_ONLINE_ALLOWED=true`, while responses disclose provider/path and treat external results as leads to verify. Response `data.metadata.semantic_fallback` can report bounded local text fallback such as `text_search` when semantic embeddings are unavailable. |

Conversation-template instantiation is non-executing by default. Quick Actions instantiate into a rendered prompt and then re-enter `/api/v1/chat`, preserving natural Soma understanding and approval before work runs. Protected Soma interaction templates are a runtime classification layer used before action execution; they map phrase themes such as private service, private data, MCP/tool enablement, team manifestation, and recurring behavior to confirmation/proposal requirements. A protected phrase can review and explain directly, but must not launch teams, bind tools, use credentials/private data, or store recurring behavior without explicit confirmation and the relevant governed proposal path.

`ConfigDocument` currently supports `apiVersion: mycelis.ai/v1` with `kind: OutcomeTemplate` or `kind: WorkerProfile`. The envelope carries stable identity/version, owner and scope, enabled state, source provenance, secret references, governance posture, and a canonical content digest. Outcome Templates shape conversation into the existing WorkIntent contract; they do not execute independently or become another durable user object. Built-in questions are bounded to three by default and four absolutely. Explicit operator values override template defaults, while policy values override both. Worker Profile specs strictly declare role, instructions, optional model or backend preference, capability refs, context bindings, usage policy, inputs/outputs, and semantic or empirical verification. They are inert catalogue templates: save, preview, activation, rollback, list, and read operations never create an agent, provider/API session, backend connection, or NATS subscription. Activation only makes a revision eligible for a later governed team selection. Runtime team creation is the sole instantiation boundary. It reads only the selected active custom revisions from the activation index using the confirmed operator, workspace, organization, then built-in boundary; hydrates only absent member fields; strips caller-supplied lineage; pins profile/provider/backend/capability lineage into the new manifest; and starts connectivity only for members included in that team. The complete effective manifest is persisted before team acknowledgement and restored exactly after Core restart without resolving the current active revision again. Team stop or mission deactivation releases its member runtime resources. Team-creation confirmations commit a durable dispatch before profile hydration so the HTTP acknowledgement and Soma composer remain responsive while the worker proceeds asynchronously. Mutable user catalogue rows are compatibility data, not a second runtime authority.

The direct-file root is `MYCELIS_CONFIG_ROOT`, defaulting to `${MYCELIS_WORKSPACE}/config`. A path input must resolve beneath that root. Soma uses the same parser and store through `preview_config_document`, `store_config_document`, and `activate_config_document`; a user may therefore ask Soma to draft a file with its governed file tools and then preview/store it, or author the YAML/JSON directly. Raw secrets are forbidden in documents; use secret references backed by `.env` or the configured secret system.

For `/api/v1/chat`, an Outcome Template preview with parseable inline YAML/JSON invokes the read-only validator deterministically and returns `mode=answer` with `payload.tools_used=["preview_config_document"]`. It creates no proposal, revision, activation, or retained artifact. Recognized Outcome Template or Worker Profile save requests with an inline document, exact activation requests, and rollback requests naming a prior version compile directly into governed proposals without provider inference; family-omitting, source-less save, and decision-shaped requests still use Soma's normal understanding path. Direct-answer inference is not authorized to execute mutation-capable tools; store and activate remain proposal/confirmation operations. A stored configuration proposal persists its originating organization, Workspace, team, and operator boundary in the approved scope, and confirmation reparses and revalidates that boundary before mutation; missing, built-in, or foreign authority fails closed. Ordinary activation accepts only the thread-selected retained revision identity and digest; rollback resolves the same trusted document identity to the exact prior version named by the operator. Atomic configuration receipts serialize turn allocation per conversation inside the mutation transaction so concurrent confirmations cannot reorder or duplicate durable thread evidence.

Confirmed store/activate tool plans return compact configuration receipts only when every executed result belongs to the synchronous configuration action. Configuration mutation and delegated/external work must use separate approvals; mixed plans fail closed. The revision or activation, exact QA ownership, run/proof state, and reloadable thread receipt commit in one transaction. Any receipt or finalization failure rolls the configuration mutation back before a failed run is retained. Purge removes only exact claimed history/revisions and restores a prior activation only when no unowned transition intervened.

External mutation work may declare `work_intent.side_effect` with `effect_kind: "external_mutation"`, `retry_safety` (`safe`, `unsafe`, or `unknown`), `idempotency_key` when the downstream capability supports stable replay, and `side_effect_state` (`not_started`, `accepted`, `committed`, or `unknown`). If its recovery deadline expires without a terminal result, Core projects `external_mutation_outcome_unknown` and a verification-first recovery option. It does not offer blind retry; same-key retry is described only for an explicitly safe contract with a non-empty key and only after external verification confirms no commit.

### Team result-contract completion

For approved team work carrying `context.result_contract`, worker completion is evidence-gated before result projection. Required retained files must map to successful output writes, and validation/proof requirements require successful readback of written output. The worker receives bounded correction opportunities; exhaustion returns `result_contract_unsatisfied` with operator-safe recovery instead of allowing model prose or declared metadata to imply completion. Server projection remains authoritative for package path, physical dependency, interaction, proof-artifact, and run/contract validation. A run id records that work started, not that a result was verified.

Command-to-worker rendering carries one compact package contract rather than duplicating acceptance and proof lists. Project-package reinference retains only the authoritative contract, a bounded path-only successful-evidence ledger, and the latest correction or interjection; generated file contents and superseded malformed responses do not accumulate. Every initial, recovery, and tool-result inference has a deadline. Malformed or incomplete mutation calls receive one safe correction for that tool target, renewed only after a successful tool execution. Game contracts reject marker-only or label-only façades unless movement and required actions mutate governed state consumed by an active rendered canvas. Operator-visible terminal diagnostics remain normalized and do not expose prompt content, provider response bodies, or tool arguments. Terminal truth remains `output_ready` only after retained, semantic, and runtime proof; otherwise work becomes `degraded` with a stable recovery path.

Functional game contracts require a bounded package shape: `index.html` is the accessible shell, `game.js` owns the state/render/interaction implementation, and `styles.css` owns presentation, alongside `README.md`, `PROOF.md`, and `project-package.json`. Referenced local JavaScript is combined with entrypoint readback for semantic inspection, so splitting writes reduces provider output pressure without weakening the functional gate. Team preparation may recommend the locked built-in builder, context analyst, media creator, and reviewer profiles, but the builder remains the sole mutation owner until ordered specialist handoffs are implemented.

Generated-package degradation classes use server-owned primary copy. `result_contract_unsatisfied`, semantic acceptance failure, runtime failure, validator unavailability/deadline, and stale-candidate validation return a bounded headline, one operator-safe explanation, and one same-team recovery action. Raw validator diagnostics remain in retained validation evidence for deliberate Inspect access; they are not copied into the primary status event, interaction summary, or recovery option. A degraded candidate remains explicitly unverified and cannot expose the verified-output open action.

For output contracts without required runtime interaction, the resulting `team_signal_result` proof uses validation source `retained_output_validation` and is limited to the shape-appropriate retained-output checks. When `work_intent.output_contract.output_validation.required=true`, result projection instead retains the complete candidate file set as `reviewing`, computes its content digest, and stages `team_output_runtime_validation` through the PostgreSQL dispatch outbox. The Core-owned Playwright adapter loads the workspace entrypoint with runtime authentication, checks page and same-origin asset failures, performs the typed primary action, and verifies its typed observation. A pass for the same digest advances the item to `output_ready`, records `runtime_output_validation` proof plus retained evidence, and only then evaluates run completion. Failure or bounded runtime unavailability advances the item to `degraded` without verified completion proof. A newer candidate digest supersedes an older validation receipt. Thread completion events are emitted only after this terminal proof boundary; `reviewing` emits a concise checking update without launch/completion affordances.

### Semantic output acceptance

`work_intent.output_contract` may include `acceptance_criteria` and `semantic_validation_required`. Interactive validation reports may return criterion-level records shaped as `{criterion, passed, evidence_refs}`. When semantic validation is required, structural files, readback, or one generic browser state change cannot alone advance work to `output_ready`; every durable criterion needs passing referenced evidence. Missing semantic proof produces `semantic_acceptance_unverified`, preserves the candidate for inspection, and keeps recovery explicit. Runtime-owned generic package recovery is eligible only for the canonical generic primary-interaction contract and fails closed for empty, mixed, or rich criteria.

Browser validation requests carry the exact ordered acceptance criteria plus explicit `check`, `probe`, `journey`, or `unsupported` mappings. Journey mappings contain bounded typed actions and observations; adapters emit criterion evidence only when that criterion's own checks pass. Unsupported criteria fail before browser launch. Game-shaped contracts currently require deterministic instructions, canvas/HUD state, and validation-action hooks for movement, attack, hazard/health, key/score, win, fail/restart, and audio so runtime proof exercises requested behavior rather than grading prose.

Output continuation context may carry `team_id`, `run_id`, `work_item_id`, `output_id`, and `content_digest` in addition to title/reference/proof. Mutating update or fork requests validate those fields against one retained durable output, compute its immutable source digest, inherit its prior output contract, and plan a distinct revision folder. Identity or digest mismatch blocks mutation.

## Framework Runs Projection Contract

`framework_runs` is an internal execution-adapter protocol, not a browser-facing replacement for Mycelis APIs. Core creates the authoritative durable run before dispatch and sends that exact `run_id` to `POST /v1/runs`; the facade does not mint a second identity. The create request carries the intent proof, execution contract, required work-item id, optional team/Outcome identifiers, idempotency key, governed source metadata, and graph revision. An identical duplicate create returns the same run; reuse of the id with conflicting identity, scope, contract, or revision fails closed.

Core now owns one durable `framework_runs`/`runs_api` binding per authoritative run, exact create-request digest, unique event-id and sequence receipts, contiguous event cursor, service/binding versions, pending approvals, and control-command CAS state. A committed external-create intent remains non-claimable as `awaiting_handler` until slice C supplies the post-commit dispatcher. The projection boundary accepts only the stored full correlation, exact kind/status pair, non-regressing service version, and next sequence; receipt, mission-event projection, and cursor advance share one transaction. Restart reconciliation and live external selection are still unavailable. After disconnect or restart, Core must resume the same binding through `GET /v1/runs/{id}` rather than creating another run. `approval_needed` must become a Mycelis-owned pending approval; only the matching governed decision may call `/v1/runs/{id}/approvals/{approval_id}`. Stop remains bound to that same run and command/version identity.

A facade or worker status of `completed` never means a Mycelis Outcome is complete. It supplies candidate outputs and execution evidence only. Core still owns path confinement, retention, digest/readback, semantic and runtime validation, proof, run/contract finalization, and user-visible recovery. Until persistence, replay/restart, approval, stop, isolation, validation, and unchanged-central proof pass together, `central` remains the only proven backend and external selection remains unavailable.

## Directed Execution Payloads

Bounded `project_package` runtime recovery may construct only the approved package shape after complete safe writes or provider failure, and must establish its own current readback. It cannot convert a semantic or browser-interaction failure into trusted completion; interactive packages remain subject to the digest-bound browser validator.

`execution_summary` is the additive directed-execution contract for Soma-facing runtime responses. It is optional for compatibility, but meaningful Soma actions should populate it as they move into the directed-execution model.

The object can include:
- `work_intent` and `execution_mode`: approved work posture, expected output shape, retention, launch hint, validation expectations, and bus/team scope when the action is proposed or confirmed. `work_intent.lifecycle` names mode-specific `stop_action`, `retry_action`, `recovery_action`, and a plain `control_summary`. `work_intent.side_effect` names external-mutation uncertainty and idempotent-retry boundaries. This metadata does not itself authorize an action.
- `intent`: original and resolved request classification
- `understanding`: Soma's concise interpretation and assumptions
- `execution`: shape, status, and summary such as `direct_soma`, `guided_proposal`, `tool_assisted_work`, or `team_execution`
- `capability_use`: governed tools, teams, MCP capabilities, automations, or plugins used
- `capability_use.reason`: operator-facing provenance detail when available, such as the active `web_search` source boundary
- `outputs`: answer, proposal, artifact, media, tool result, retained team, retained file/code output references, or `project_package` deliverables. Browser clients may preview image/audio/video output URLs inline when the MIME type or file extension is recognizable, while durable file paths stay available through workspace reveal. Confirmed execution outputs may also include `output_class`, `proof_artifact_id`, `open_url`, and a per-output `proof` envelope with run/contract linkage, path-boundary status, readback status, checksum metadata, storage ref, and recovery hint. `output_class` values are `user_deliverable`, `planning`, `internal_handoff`, `proof`, and `source_material`; clients should treat only `user_deliverable` as default Outcome/Vault/Resources delivery.
- `outputs[].kind=project_package`: retained complex deliverable package for generated projects such as playable browser games. Package outputs may include `entrypoint`, `folder`, `files`, and `validation`; generated file packages also include support files such as `README.md`, `PROOF.md`, and `project-package.json` when requested or inferred. The UI should expose the entrypoint as the primary open action, the folder through workspace reveal, the package folder through Resources deep-linking, the file list as source context, and validation as proof context. Confirmed `write_file` and `store_artifact` executions can both produce this output shape; `store_artifact` should use artifact `type="project_package"` or metadata `package_kind/output_kind/kind="project_package"` with `entrypoint/package_entrypoint`, `folder/package_folder`, `files/package_files`, and `validation/validation_summary` metadata. A synchronous confirmed package is trusted only when its entrypoint is readable inside the assigned `groups/{team_id}/...` workspace; a missing or general-bucket package remains degraded without a trusted deliverable ref. Governed worker completion likewise uses successful tool evidence rather than declarations: every required file and referenced local dependency must have a current write, validation markers must be rendered attributes, and Core performs an exact runtime-owned read of the latest entrypoint after static checks pass. A corrected result with the same output ID supersedes its stale candidate before digest and validation. A later write invalidates earlier readback; truncated, stale, or divergent content cannot prove package completion. Interactive packages then remain `reviewing` until the digest-bound browser validator proves the approved observable behavior.
- `proof`: `run_id`, `audit_event_id`, `intent_proof_id`, and verification state
- `audit_recovery`: approval status, recovery state, blocker, retry posture, and optional `degradation`
- `audit_recovery.degradation`: operational degradation metadata covering `code`, `what_failed`, `trusted_state`, `invalidated_proof`, `safe_continuation`, and `requires_attention`
- `next_step`: suggested continuation or proof/review link

Current producers:
- `/api/v1/chat` direct answers and guided proposals
- `/api/v1/intent/confirm-action` verified proposal execution results, failed approved-execution recovery summaries, retained tool outputs, run-conversation turns, durable team-work records for confirmed `create_team`, delegation, and retained deliverable tool calls, plus durable `outcome_project` ownership when team-work/output refs exist
- `/api/v1/organizations/{id}/workspace/actions` Team Lead guidance responses with proof explicitly left unrun until execution exists
- `/api/v1/groups/{id}/broadcast` accepted group broadcasts with `audit_event_id` proof and no fabricated `run_id`

Implementation notes:
- use `/api/v1/brains` and `/api/v1/cognitive/providers/{id}` to manage the provider inventory exposed in the product
- provider secrets resolve through env/secret references; raw `api_key` update payloads are rejected by provider-management APIs
- provider reads never return raw secret values; safe configuration responses may expose configured/readiness posture only
- LiteLLM is an optional model gateway, not an execution backend: Core still owns data-boundary/provider eligibility, profiles, approvals, semantic budgets, audit, and proof; gateway fallbacks may not cross an approved boundary
- `model_gateway` is infrastructure-owned and not a raw-key/browser control. Gateway inference from authoritative swarm scope carries only a keyed pseudonymous correlation value; direct and other non-swarm inference remains uncorrelated in this slice.

- `upstream_response_id` is the opaque response-body identifier reported by the selected OpenAI-compatible upstream. It is not a LiteLLM call/spend-log request id, Mycelis run id, audit id, or proof of end-to-end correlation; none of these accounting fields is a cost record or Outcome proof
